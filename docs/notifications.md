# Notificações internas — após v0.1.0

O perfil `admin` é o super administrador do painel. A migração 026 cria tipos de alerta, ocorrências e recibos por administrador. O worker lê o retrato operacional a cada minuto. Uma ocorrência por tipo permanece aberta enquanto a condição existir; quando ela some, a ocorrência é resolvida. Se reaparecer, uma nova ocorrência é criada. Uma falha ao obter o retrato não resolve ocorrências por engano. O worker usa lock transacional e índice único parcial para evitar duplicatas entre réplicas.

Todos os tipos aparecem no sininho e na tela `/notificacoes`, somente para administradores. A tela oferece histórico paginado, filtro de não lidas, tamanho de página, ordenação por data/tipo e leitura individual. O status de leitura é próprio de cada administrador. Operadores e viewers não acessam os endpoints nem recebem notificações. Não há telefone, texto SMS/MO, URL de callback, token ou segredo nas notificações.

Na mesma tela, o administrador define globalmente quais tipos também geram e-mail. O padrão é **desligado para todos**. A preferência é capturada quando uma nova ocorrência começa; alterar a opção não envia e-mail de ocorrências anteriores. Para um tipo ativado, o banco cria um recibo de entrega para cada `system_user` ativo com papel `admin`. O worker usa o SMTP já configurado para convites/recuperação, envia descrição e link para o painel, e marca a entrega individual. Tentativas com lease e até oito falhas são persistidas; após falha, a próxima tentativa ocorre cinco minutos depois. A entrega é pelo menos uma vez: se SMTP aceitar e a confirmação no banco falhar, um e-mail pode ser repetido. A tela impede ativar e-mail sem SMTP configurado no backend.

Tipos atuais: resultado incerto sem DLR final, lease expirado, DLR/MO pendente há 15 minutos, DLR/MO sem envio associado há 15 minutos, SMS agendado atrasado há 5 minutos e callback ao cliente com falha definitiva na última hora. A descrição usa apenas contagens e regra operacional. Os limiares são os mesmos da Visão geral. Isso não é alerta de indisponibilidade da própria API: se banco/API/worker falharem, um monitor externo ainda será necessário.

Aplicar a migração 026 antes de iniciar binários novos. O schema é aditivo; rollback do binário pode preservar as tabelas e preferências sem efeito. Não remover a migração ou apagar recibos para reverter, pois isso pode repetir e-mails. O e-mail só pode sair quando há SMTP válido e uma preferência ativada. HML/produção exigem confirmar configuração SMTP e destinatários administrativos antes de habilitar tipos.

Em 30/10/2026, HML recebeu a migração 026, API, frontend e worker. A primeira ocorrência gerou dois recibos administrativos; a consulta ao banco confirmou zero tipos com e-mail ativado. Argo CD mostrou os três componentes saudáveis e os endpoints públicos de saúde/frontend responderam HTTP 200. O SMTP real não foi testado nesta liberação.
